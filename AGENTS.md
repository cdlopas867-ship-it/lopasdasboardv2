## Base44 dev environment

- **Stack**: TanStack Start (SSR via nitro) + Vite 8 + React 19 + Supabase. Package manager is **bun** (`bun.lock`, `bunfig.toml`), but the container runs on the **`node:22`** image and executes Vite via Docker/Compose.
- **Run**: `docker compose -f docker-compose.base44.yml up -d`. The dev server (`vite dev`) listens on **port 3000** (overridden via `--port 3000` CLI flag; the Lovable config defaults to 8080). See `docker-compose.base44.yml` and `package.json` for local start commands.
- **Como o dev server é iniciado (não é erro)**: o serviço `web` roda `npm i -g bun && bun install --frozen-lockfile && exec ./node_modules/.bin/vite dev --port 3000 --host 0.0.0.0`. O Vite é chamado pelo **binário local**, não por `npx`: quando o platform para/recria o stack (SIGTERM no processo), o wrapper do npm imprimia um bloco de erro enganoso no log do serviço — `npm error path /app`, `npm error command failed`, `npm error signal SIGTERM` — que parecia falha da aplicação, mas era só o npm morrendo no desligamento. Com o binário local o desligamento é silencioso. Verificação: `docker compose -f docker-compose.base44.yml logs web` não traz mais linhas `npm error` (o `npm notice` de versão, quando aparece, também não é erro); `npm error` volta a significar falha real de dependência.
- **Timezone**: the compose sets `TZ=America/Sao_Paulo` on the `web` service — the app's date logic assumes it. `parseModificado` (`drive-auto-import.ts`) reads the Drive folder view dates (e.g. `"Oct 7"`, no hour) as **server-local** midnight, and the panel formats the resulting instant in the browser's zone. With the container in UTC the selo "Atualizado" shifted back 3 h and showed the **previous day** (e.g. `06/10 21:00` for an `Oct 7` file). Do not drop this env var.
- **Env vars**: `.env.base44-defaults` holds non-secret placeholders (Supabase publishable keys, gate credentials `lopas`/`cd`, service-role placeholder). Real secrets land in `/run/base44/...` and are injected into the container environment. Note que `SESSION_SECRET` **não** está em nenhum dos dois: `gate.server.ts` tem um fallback interno, então o app sobe, mas o cookie do gate fica assinado com essa string fixa enquanto o segredo não for entregue — trocar o segredo invalida as sessões abertas.
  - `SESSION_SECRET` — **required at boot**; the site-access gate (`gate.server.ts`) throws without it. Generated for development.
  - `SUPABASE_SERVICE_ROLE_KEY` — needed for live Supabase data (historico/sync/valor-faturado stores). Without it, APIs fail gracefully and the dashboard shows built-in sample data (`initialSyncData`).
  - `SITE_USERNAME` / `SITE_PASSWORD` — gate login credentials. Defaults in `.env.base44-defaults`.
- **Auth flow**: `AuthProvider` calls `checkAccess()` server fn on mount → redirects to `/login` if not unlocked. Login calls `unlockSite()` which checks `SITE_USERNAME`/`SITE_PASSWORD` and sets the session cookie.
- **Not a Lovable sandbox**: `LOVABLE_SANDBOX`/`DEV_SERVER__PROJECT_PATH` are not set, so the Lovable vite config runs in non-sandbox mode (no strictPort, host `::`). The `--host 0.0.0.0` flag ensures access from the container/preview origin.
- **Vite host allowlist**: `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` is passed bare in the compose `environment:` so Vite >= 6.1 accepts the preview origin.
- **Fotos do Lopas no preview**: as imagens do painel (fundos das cenas via `ResumoBg`/`FOTOS_RESUMO`, carrossel do login via `LoginBgCarousel`/`FOTOS_LOGIN`, tela de boas-vindas e o `preload` de `src/routes/__root.tsx`) são assets **hospedados pelo Lovable**, em `/__l5e/assets-v1/<id>/<arquivo>` — caminhos que só a hospedagem do Lovable serve. Fora dela respondiam **404** e o painel ficava sem fundo (`Failed to load resource: 404` para cada foto). Com `BASE44_PREVIEW_MODE=1` o plugin `fotosPreviewBase44` em `vite.config.ts` (`apply: "serve"`) serve uma **foto equivalente de `public/`** nesses caminhos (escolha estável pelo nome do arquivo); sem o flag o plugin não é registrado e o Lovable segue com os assets reais — nenhum código do app mudou. O flag chega ao container pela linha **`- BASE44_PREVIEW_MODE`** no `environment:` do serviço `web` no `docker-compose.base44.yml`. Verificação (com o flag): `curl -o /dev/null -w '%{http_code}' http://localhost:3000/__l5e/assets-v1/x/lopas-aerea-jardim.webp` → `200 image/jpeg`, e numa carga limpa do preview nenhum recurso `/__l5e/...` falha (`performance.getEntriesByType('resource')` → `responseStatus: 200`).
- **Cancelamento de SSR no preview**: quando o navegador, proxy ou HMR encerra uma requisição antes da resposta SSR terminar, o Node lança `Error: aborted`. Isso é uma desconexão esperada — não uma falha da aplicação — e antes chegava como 500 nos logs. `isRequestAborted` em `src/lib/error-capture.ts` identifica apenas `AbortError`/mensagem `aborted` (incluindo a cadeia `cause`); o wrapper de `console.error` não registra esse caso, e `src/server.ts` devolve uma resposta vazia 499 sem log. Todos os demais erros continuam registrados e retornam a página de erro. Dois caminhos escapavam desse tratamento e voltavam a sujar o log (vistos em 14/10, ~10 s depois de recriar o container, com requisições pendentes do proxy/navegador): (1) o servidor de dev do TanStack registra o caso **já formatado como string** (`[ssr] erro não tratado:\nError: aborted\n at abortIncoming…`), que o wrapper não reconhecia porque não é um `Error` — coberto agora por `isAbortedLogText` (mesma regra: a linha do erro é exatamente `aborted`); (2) o h3 troca a causa por um 500 genérico (`{"status":500,"unhandled":true,"message":"HTTPError"}`) e o `src/server.ts` convertia isso em página de erro **com log**, sem como saber que a requisição havia morrido — agora, quando `request.signal.aborted` está ligado, devolve 499 sem log (ninguém está esperando a resposta). Verificação: uma carga/reload do preview não produz `[ssr] erro não tratado: Error: aborted` nem `[server] falha ao processar requisição` nos logs; `/` permanece 200. O filtro é testável sem reproduzir a desconexão — dentro do container: `docker compose -f docker-compose.base44.yml exec -T web node --experimental-strip-types --input-type=module -e '…'` importa `src/lib/error-capture.ts`, troca `process.stderr.write` por um coletor e confirma que `console.error("[ssr] erro não tratado:\nError: aborted\n at …")` não escreve nada (`suppressedAbortedLines: 0`), enquanto `console.error("Error: boom")` continua escrevendo (`realErrorLines: 1`).
- **Drive sync (real hours)**: `drive-auto-import.ts` checks the user's Drive folder every 15 s in the background and on each `/api/sync-data` GET (10 s throttle). Without gateway keys, the app lê a pasta **pública** direto (HTML do `embeddedfolderview` + `docs.google.com`/`drive.google.com`). Se as chaves do gateway **existirem mas a conexão estiver revogada/expirada** (o gateway responde `401 Invalid API key`), a listagem e o download agora **caem para esse acesso público** em vez de abortar: antes, qualquer falha do gateway derrubava a importação inteira e o painel ficava parado no `initialSyncData` (sintoma: "não sincroniza com o Drive"). Verificação: com `LOVABLE_API_KEY`/`GOOGLE_DRIVE_API_KEY` falsas injetadas num override de compose o log mostra `gateway do Drive indisponível — lendo a pasta pública` e ainda assim grava `histórico salvo`; sem as chaves o log não traz aviso de gateway. O selo no topo do painel (**"Atualizado DD/MM/AAAA HH:MM"**) mostra a **hora real da atualização no Drive**: `construirSincronizacao.em` é a **modificação mais recente** entre as planilhas da pasta (fallback: instante da leitura) — não o horário da checagem. `planilhas[].modificado` alimenta a lista do popover do selo.

- **Sync do painel (client)**: `use-dados-sync.ts` aplica o payload recebido só quando a "chave" (`dataKey`) muda, para evitar re-render no polling. Essa chave **precisa incluir todo bloco que pode mudar sozinho** — `producaoSemanal` foi adicionado (`prodSig`: dias + totais de ton./un.); sem ele, uma atualização só da planilha de produção não mudava estoque/resumo e o painel **ignorava** o novo payload, deixando a cena "Produção da Semana" congelada (ex.: 0%). - **Produtividade** (cena 13 de 14, `src/components/CenaProdutividade.tsx`): só a produtividade — a **lotação de pessoal (QLP · CD)** voltou a ser cena própria (a 12). Botões (`ToggleSecoes` de `cena-interativa`) alternam o **tipo de atividade**; para o tipo ativo mostra o `DestaqueGradiente` com o **total em toneladas** e dois quadros lado a lado (top 6): **colaboradores** (nome, cargo · turma, tempo de casa, toneladas e % do tipo) e **por turma** (toneladas, nº de colaboradores e %). Dados **estáticos** em `src/data/produtividade.ts` (`PRODUTIVIDADE.tipos[]`), extraídos das planilhas **`PRODUTIVIDADE POR COLABORADOR`** (aba `Resultado`) da **pasta do Drive**, baixadas em 07/10/2026: uma planilha por tipo de atividade — `separacao-manual` ("separação manual"), `separacao-empilhadeira` ("separação com empilhadeira"), `recebimento` ("1 recebiemnto") e `movimentacao` ("movimentação"); o relatório de id 7 era **idêntico** ao manual e foi descartado. Cada tipo tem o próprio **`periodo`** (o componente exibe `tipo.periodo`, não o período global): separação **06/01/2026 a 07/10/2026**; recebimento e movimentação **01/04/2026 a 31/08/2026**. Estrutura do relatório: linha 1 = título, linha 2 = **tipo de atividade** (em branco quando não há filtro), linha 3 = cabeçalho `DIA, COD_COLABORADOR, NOME, TURNO, QTDE_TAREFAS, PESO, CX`, depois uma linha por dia × colaborador (rodapé com o copyright da FullSoft). `ton` = **PESO (kg) somado ÷ 1000**, `cx` = CX somado. **Cargo, tempo de casa e turma NÃO vêm do relatório**: são casados pelo NOME com a `CD - QLP.xlsx` (aba `Base`) — o relatório usa **nome curto/apelido** (`JULIO BARBOSA`) e o cadastro o nome completo (`JULIO CESAR BARBOSA MADEIRA`), então o casamento exige que **todos os tokens** do nome curto apareçam no nome completo (empate → prefere `CONTADOR = 1`); isso casa ~87/117 no manual e ~75/98 na empilhadeira. Logo **abaixo dos dois quadros**, o componente **`ComparativoProdutividade`** compara a **atividade ativa × Carregado** no mesmo período (mesma janela de meses): duas barras (atividade e Carregado) e a **diferença (atividade − carregado)**, em toneladas e %. O Carregado mensal vem de `src/data/carregado-mensal.ts` (`CARREGADO_MENSAL`, Jan–Set/2026: jan–abr da planilha "Toneladas Mensal" = mesmos valores de `CARREGADO_SEM_DRIVE`; mai–set da aba "Gerenciamento Carregamento" da planilha pública `1cvc8dD1_jDPZ7bXWnyw7cwQEniS0LI2V`), somado por `carregadoNoPeriodo(periodo)` — só entram os meses cobertos pelo período do tipo; **setembro está parcial (até 11/09)** e outubro não tem carregado lançado, então o carregado cobre jan–set enquanto a separação vai até 07/10 (a diferença embute essa sobra de dias). É **dado estático**, igual à produtividade: ao atualizar, reextrair os meses da planilha. Em seguida, o componente **`DestaquesProdutividade`** mostra os **"Destaques do mês"** (top 3 **melhores** ▲) por **equipe**, definida pelo **cargo/função** (`equipeDoCargo`): **Equipe Separação** = cargos de expedição/etiquetagem, **Equipe Estoque** = cargos de estoque/empilhadeira/carga e descarga/arrumador. Colaboradores com `ton = 0` ou cargo não casado ficam fora; usa sempre o tipo de atividade ativo (mesmo período/totais). Clicar num colaborador do ranking expande a **ficha QLP** da linha (turno, turma, cargo, função, cidade, tempo de casa e admissão) e pausa o painel; o clique usa `stopPropagation` para não virar navegação de cena. A ficha vem de `src/data/qlp-fichas.ts` (`FICHAS_QLP`, mapa nome → ficha, mesma regra de casamento por nome; cargo/turma/tempo repetem o ranking, turno/função/cidade/admissão vêm do cadastro) — 108 dos 142 nomes casam; os demais mostram "sem cadastro QLP". Para atualizar, reextrair a `CD - QLP.xlsx` com o script `/tmp/gen-fichas.cjs` (copia a planilha para o container e roda `node`).
- **Drive — formato atual (sem aba Resumo)**: a pasta hoje entrega planilhas de posição (`estoque NN.xlsx`, modelo `ESTOQUE 001 - POSIÇÃO DE ESTOQUE`) **sem aba `Resumo`**. O resumo do painel é calculado a partir dos itens (`lerItensEstoque` + `resumoDeItens`) e a data-base vem da modificação do arquivo de itens. As planilhas `public/planilhas/*` são apenas fallback: o `mtime` delas é o do checkout (sempre "agora"), então **não** deve entrar na comparação de recência `melhorItensMod > melhorResumoMod` — senão o resumo local antigo vence os itens atualizados do Drive e o painel congela. - **Produção da Semana**: a cena usa `calcularProducaoSemanal` (`src/lib/producao-semanal.ts`), que lê a planilha **PCP 003 - Análise de Realização Total** (`produção NN.xlsx`): `produzido` = QTDE ENTREGUE / PESO REALIZADO (kg), `previsto` = programado e `pendente` (a produzir) = previsto − produzido. O `recebido`/`entregue` vem da planilha **PESO RECEBIDO POR PERÍODO** (`calcularRecebidoPorDia`). A cena mostra a **semana atual** (seg–dom, `semanaAtual`) para misturar produzido/recebido (dias passados) com a produzir (dias futuros). Dois cuidados: (1) a planilha de **pendências** PCP 004 também tem DT INICIAL/PENDENTE e era confundida com produção (o parser pegava a última processada e zerava a tonelagem) — `calcularProducaoSemanal` agora a ignora pela coluna `PESO PENDENTE`; (2) o cabeçalho da PESO RECEBIDO usa `DT_INICIO`/`PESO_RECEBIDO` com underline — `normalizeHeader` remove underlines além de espaços, senão o recebido nunca era encontrado. A cena usa o **formato resumido**: donut interativo + toggle de **Recebido × Diferença (o que falta receber)** (`DonutInterativo`/`ToggleSecoes`/`useFocoCena` de `cena-interativa`), card com % e tonelagem do foco e tabela **Legenda** (Recebido + Diferença da semana, un./ton./%). Os dois botões são **Recebido** e **Diferença (o que falta receber)**: o % no meio da rosca é sobre o peso previsto da semana — Recebido = `pctRecebido = totalTonRec / totalTonPrev` e Diferença = `100 − pctRecebido` (previsto é a base). A cena também traz uma tabela **Dia a dia** (produzido × recebido, toneladas e unidades) montada diretamente de `semanaAtual(dias)` (agrupados pela data final) — não há nova fonte de dados. Na coluna **Produzido** a tonelagem exibida é o **peso previsto** (`tonPrevisto` / PESO PREVISTO), não o PESO REALIZADO, junto das unidades produzidas (`produzido` / QTDE ENTREGUE); **Recebido** usa `tonEntregue`/`entregue`. Cada célula mostra também a **variação de um dia para o outro em %** (componente `VariacaoDia`: `(atual − anterior) / anterior`, ▲ verde sobe / ▼ vermelho desce), calculada sobre a tonelagem de Produzido e de Recebido; o primeiro dia da semana não tem variação. Uma quarta coluna **Média** traz a tonelagem média por ordem de produção do dia (`tonPrevisto / ordens`, exibida como `17,6 t` com a legenda "por ordem"; `—` quando o dia não tem ordens ou tonelagem).
